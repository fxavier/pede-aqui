# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Multi-tenant delivery marketplace MVP ("Pede Aqui") targeting Mozambique. Four distinct applications share a single monorepo:

| Directory | Tech | Role |
|---|---|---|
| `backend/` | Java 21 + Spring Boot | REST API, Keycloak JWT auth, Flyway migrations |
| `pede-aqui-backoffice/` | Next.js 15 + TypeScript | Backoffice (admin/ops/finance/vendor/support) |
| `pede-aqui-delivery/` | React 18 + Vite + TypeScript | Customer-facing delivery web SPA |
| `pede_aqui_delivery_app/` | Flutter + Dart | Customer mobile app |
| `pede_aqui_courier_app/` | Flutter + Dart | Courier (estafeta) mobile app |

Repo layout notes (cleaned up in LAC-57; the pre-cleanup tree is preserved in tag `archive/pre-cleanup`):

- The old `web/` Next.js prototype (and its `backend/web/` copy) was removed — all backoffice work is in `pede-aqui-backoffice/`.
- Spec/agent tooling lives only at the root (`specs/`, `openspec/`, `.specify/`, `.opencode/`); the stale copies under `backend/` were removed. `backend/scripts/` stays (live ADR-0001 SQL scripts).
- Diagram/binary exports (`architecture.*`, `system-flow.*`) live in `docs/assets/`; root `*.pdf/*.png/*.svg/*.pptx/*.docx/*.tgz` are git-ignored, so put new binaries there.
- Superseded root reports `AUDIT.md`, `PLAN.md`, `REPORT.md` (2026-07 audit round) live in `docs/history/`; current assessments are in `docs/assessment/`.
- Local clones may still contain a nested `backend/.git` repo from the old layout. It is not tracked by the root repo — remove it manually (`rm -rf backend/.git`, after archiving a bundle if you care about its history).

`infra/` and `admin/` hold two Terraform root modules for S3 upload storage (`infra/` = static CORS apply, `admin/` = privileged bootstrap) — see the Storage section.

Local services run via Docker Compose: PostgreSQL (PostGIS), Redis, Keycloak, MinIO, Prometheus.

## Local Development

### Start infrastructure

```bash
docker compose up -d postgres redis keycloak minio minio-init
```

(`minio-init` creates the `pede-aqui-uploads` bucket used by the backend's `dev` profile; it's idempotent.)

MinIO images come from Bitnami's frozen public archive (`bitnamilegacy/minio:2024.10.13-debian-12-r1` = MinIO `RELEASE.2024-10-13T13-34-11Z`, `bitnamilegacy/minio-client` for `minio-init`), used by both compose and `MinioUploadLimitsIntegrationTest`. Don't switch back to `minio/minio`/`minio/mc` (removed from Docker Hub) or `quay.io/minio/*` (needs login) — CI cannot pull them. The Bitnami entrypoint starts the server itself, so pass no `command`.

### Backend (Spring Boot)

```bash
cd backend
mvn spring-boot:run
# OpenAPI UI: http://localhost:8080/swagger-ui.html
```

Run a single test class:

```bash
cd backend
mvn test -Dtest=SupportTicketServiceTest
```

Full verify (compile + tests):

```bash
cd backend && mvn clean verify
```

API contract: `docs/api/openapi.json` is generated by `OpenApiContractExportTest` (needs Docker) and committed. Any change to controllers/DTOs that alters the API must regenerate it in the same PR (`cd backend && mvn test -Dtest=OpenApiContractExportTest -Dopenapi.output=../docs/api/openapi.json`) — CI fails on a stale file, and fails on oasdiff breaking changes unless the PR has the `api-breaking` label (then add an `API-MIGRATION.md` entry). Details: `docs/api/README.md`.

Spring profiles: `dev` is the default (`spring.profiles.default`) and points storage at local MinIO — no AWS needed. `prod` (`SPRING_PROFILES_ACTIVE=prod`) targets real AWS S3 and fails fast if `AWS_S3_BUCKET`/`AWS_REGION` are missing. See the Storage section. `prod` also fails fast without `APP_DELIVERY_CODE_HMAC_SECRET` (delivery-PIN HMAC key; only `dev` has a default).

Secrets: `application.yml` has **no literal defaults** for `DB_PASSWORD`, `KEYCLOAK_ADMIN_CLIENT_SECRET` or `APP_DELIVERY_CODE_HMAC_SECRET` — the local values live only in `application-dev.yml`. In `prod`, `RequiredSecretsProperties` (`@Validated @NotBlank`, bound via `app.secrets.*` in `application-prod.yml`) aborts startup if any of them is blank, and every `DataSource` depends on it so the error surfaces before Flyway touches the DB. New secrets follow the same pattern (no default in base yml, dev default in `application-dev.yml`, field in `RequiredSecretsProperties`). `prod` also disables `/api-docs` and Swagger UI.

```bash
cd pede_aqui_courier_app
flutter pub get
flutter run

# With Keycloak PKCE (Android emulator)
flutter run -d android \
  --dart-define=API_BASE_URL=http://10.0.2.2:8080/api/v1 \
  --dart-define=KEYCLOAK_ISSUER=http://10.0.2.2:8081/realms/delivery \

```

On an Android emulator use `10.0.2.2` to reach host services (as above); on an iOS simulator use `localhost` for the same `--dart-define` URLs. Keycloak redirect URIs must be registered per client exactly as shown. The `KEYCLOAK_*` values above are also the code defaults (customer app defaults the issuer to `localhost:8081`, courier app to `10.0.2.2:8081`), so only `API_BASE_URL`/`KEYCLOAK_ISSUER` usually need overriding. Both apps default to `USE_MOCK_DATA=true` (fake login + data, no Keycloak); add `--dart-define=USE_MOCK_DATA=false` to hit the real backend and Keycloak — a release build refuses to start with mocks on.

**Issuer gotcha:** Keycloak stamps `iss` from the hostname the app used, and the backend validates `iss` against `KEYCLOAK_ISSUER_URI` (`http://localhost:8081/realms/delivery`). Tokens obtained via `10.0.2.2:8081` are therefore rejected by a backend on the host (401). On an Android emulator/device prefer `adb reverse tcp:8081 tcp:8081 && adb reverse tcp:8080 tcp:8080` and use `localhost` in both `API_BASE_URL` and `KEYCLOAK_ISSUER`.

## Backend Architecture

### Package layout (`com.delivery`)

Each domain (e.g. `order`, `vendor`, `dispatch`, `finance`, `support`) owns its own sub-package tree:

```
controller/    REST endpoint, request validation, response DTOs
service/       Business logic, transactions, tenant/role checks, state transitions
repository/    Spring Data JPA (no custom tenant filtering here)
entity/        JPA table mappings
dto/           Request and response payloads
mapper/        Entity ↔ DTO conversion
```

Cross-cutting packages: `common/config`, `common/exception`, `common/security`, `common/ratelimit`.

Domain packages: `auth`, `cart`, `catalog`, `customer`, `dashboard`, `delivery`, `dispatch`, `finance`, `geo`, `inventory`, `marketing`, `notification`, `order`, `payment`, `rating`, `settlement`, `support`, `tenant`, `upload`, `vendor`.

### Security

- Keycloak JWT tokens. `JwtRoleConverter` maps `realm_access.roles` into `ROLE_<name>` Spring authorities.
- `SecurityConfig` opens **for `GET` only**: `/actuator/health/**`, `/livez`, `/readyz`, `/api-docs/**`, `/swagger-ui/**`, and the public browse endpoints `/api/v1/catalog/categories`, `/api/v1/catalog/vendors/*`, `/api/v1/catalog/vendors/*/products`, `/api/v1/search/vendors`. The only anonymous writes are `POST /api/v1/register` and `POST /api/v1/customers/register`. Everything else requires a valid JWT — an anonymous POST/PUT/PATCH/DELETE is always 401 (LAC-02; guarded by `AnonymousWriteEndpointsApiTest`, which enumerates every mapped write endpoint — a new public write must be added to both `SecurityConfig` and that test's allow-list). Never add a `permitAll` matcher without an `HttpMethod`.
- **User role assignment (LAC-13)**: `POST /api/v1/admin/users` is ADMIN-only (`SUPPORT` keeps `GET /admin/users[/{id}]`). Remember a method-level `@PreAuthorize` *replaces* the class-level one. Assignable roles come from the allow-list in `AppUserProfileService` (`ASSIGNABLE_BY_CALLER_ROLE`): ADMIN assigns every role except `ADMIN`; only the platform admin (no `tenant_id`) may also assign `ADMIN`; anything else → 403 `role_assignment_forbidden`, empty roles → 400 `roles_required`. The roles are mirrored to the existing Keycloak user via `KeycloakAdminService.assignRealmRoles` (a Keycloak failure rolls the profile back) and audited as `USER_ROLES_ASSIGNED`.
- Actuator: on the application port everything except health/probes (`metrics`, `prometheus`, `info`) requires `ADMIN`. When `MANAGEMENT_SERVER_PORT` is set (default `8091` in `prod`; compose sets it too) actuator moves to that internal port, where `/actuator/**` needs no token so Prometheus can scrape (`prometheus.yml` → `backend:8091`). That port must never be published by ingress/LB; on the public port probes are `/livez` and `/readyz`.
- Keycloak realm (`keycloak/delivery-realm.json`): `sslRequired: external`, brute-force protection on. `delivery-app` (backoffice) and `pede-aqui-web` (customer web) are public clients, **code + PKCE S256 only** (`directAccessGrantsEnabled: false`, LAC-10): `delivery-app` since W4-D (redirect URIs `http://localhost:3000|3001/api/auth/callback/keycloak`, post-logout `…/login*`), `pede-aqui-web` since W4-C (post-logout redirect `http://localhost:5173/`, `:4173/`). `pede-aqui-mobile` / `pede-aqui-courier-mobile` are code+PKCE only (no ROPC; post-logout redirect = their redirect URI, so app logout ends the SSO session); the Flutter customer and courier apps log in through them with Authorization Code + PKCE (W4-E, see Flutter App Architecture) and no longer call ROPC. Scripts needing a password-grant token use the dev-only client from `scripts/lib/keycloak-dev-ropc-client.sh` (local Keycloak only); `KeycloakMerchantRegistrationE2ETest` creates a throwaway one in its container and asserts `delivery-app` refuses ROPC.
- Realm hardening (LAC-09, realm part): `passwordPolicy` = `length(10) and digits(1) and upperCase(1) and lowerCase(1) and notUsername and passwordHistory(3)` (applies to new/changed passwords and to import). Registration mirrors it: `@PasswordPolicy` (`auth/validation`) on both registration DTOs → 400 `validation_failed` on `password`; a Keycloak policy rejection maps to 400 `password_policy_violation`; backoffice/web register pages share the rule (`src/lib/password-policy.ts`). Keep all of these in sync with the realm. The Flutter customer register screen mirrors it too (`features/auth/data/password_policy.dart`). Lifetimes: access token 5 min, SSO idle 30 min / max 10 h, offline idle 30 days; **refresh-token rotation** (`revokeRefreshToken=true`, `refreshTokenMaxReuse=0`): every refresh returns a new refresh token and reusing an old one fails, so clients must store the new token and never refresh in parallel (both Flutter apps' `ApiClient` interceptors and `OidcSession.refresh()` are single-flight for this reason).
- TOTP (HmacSHA1/6 digits/30 s) is mandatory for realm roles `ADMIN`, `FINANCE`, `OPS` via the custom browser flow `browser-privileged-mfa` (mutually exclusive "Condition - user role" subflows + OTP Form; unconfigured users get `CONFIGURE_TOTP` on first browser login). **It only applies to the browser/code flow** — the direct-grant (ROPC) flow is the Keycloak default, which asks for OTP only if the user already configured one. The backoffice now logs in through the browser flow (PKCE, LAC-10), so TOTP is effective for privileged backoffice users; the only remaining ROPC client is the local dev-only script client, which bypasses it.
- **Customer phone + SMS login (LAC-18, W5-D, ADR-0004 *Proposed*)**: Keycloak provider in `keycloak/extensions/sms-otp` (standalone Maven project against the Keycloak 26.8.1 SPI — not a backend module; `mvn verify` there runs unit tests + `PhoneOtpKeycloakIT`, a real Keycloak container with the jar and this realm; the IT fails rather than skips without Docker — opt out only with `-DskipITs`; its HTTP helper keeps cookies by hand because Keycloak's login cookies are `Secure` and `java.net.CookieManager` drops them on http). Authenticator `pede-aqui-phone-otp` in flow `browser-customer-phone`, bound by `authenticationFlowBindingOverrides.browser` **only** to `pede-aqui-web` and `pede-aqui-mobile`: phone screen → SMS code, or "email e palavra-passe" (ATTEMPTED → the password alternative, which keeps copies of the privileged TOTP subflows); a non-phone `login_hint` skips to the password form. Rules live in `PhoneOtpEngine` (pure Java, unit-tested): 6 digits, TTL 5 min, stored only as HMAC-SHA256 in auth-session notes; 5 wrong codes **per phone** → progressive lock (15 min × 2^n, ≤ 24 h); 20 per IP → IP lock; resend cooldown 60 s; 3 SMS/phone and 10/IP per 15 min; counters in `SingleUseObjectProvider` under HMAC keys (no raw phone/IP). Values are the `customer-phone-otp` authenticator config. E.164 with Mozambique default (+258, mobiles 82–87) — `PhoneNumbers` in the provider mirrors backend `auth/validation/PhoneNumberE164`; keep them in sync. First login creates `phone-<uuid>` + `CUSTOMER` + attributes `phone_e164`/`phone_verified` (declared in the user profile, admin-edit only; `email` is no longer required there). Users with any role in `blockedRoles` (all staff roles) are refused. SMS goes through the custom `sms-sender` SPI; only the stub `log` exists (masked number + masked code; the code is logged only with `KC_SPI_SMS_SENDER__LOG__REVEAL_CODE_IN_DEV_MODE=true` under `start-dev`). A real gateway = new provider jar + `--spi-sms-sender--provider=<id>`. `KC_SPI_AUTHENTICATOR__PEDE_AQUI_PHONE_OTP__HMAC_SECRET` (≥ 32 chars, same on all nodes) is mandatory in production mode. Compose builds Keycloak from `keycloak/Dockerfile` (jar baked in) — the realm needs the provider, so never run customer logins on the bare upstream image. Tokens of the two customer clients carry `phone_number` / `phone_number_verified`; `TenantRequestFilter` → `CustomerProfileProvisioningService.syncVerifiedPhone` copies a verified, valid number to `app_user_profiles.phone_e164` (one SELECT when unchanged; a number already on another profile of the tenant is skipped with a masked WARN) and `GET /me` returns `phoneE164`/`phoneVerifiedAt`. The backend never generates or checks codes.
- Realm vs dev users: `keycloak/delivery-realm.json` is environment-neutral (only service-account users). Human dev users live in `keycloak/dev-users.json`, mounted by docker-compose as `/opt/keycloak/data/import/delivery-users-0.json` (Keycloak's dir import picks up `<realm>-users-<n>.json`). Dev seed logins: `admin`/`Admin12345` (ADMIN, no tenant), `finance`/`Finance12345`, `support`/`Support12345`, `ops`/`Ops1234567`. Never mount `dev-users.json` outside local dev. Realm changes only take effect on a fresh import (`--import-realm` skips an existing realm): `docker compose rm -sf keycloak && docker compose up -d keycloak`.
- Fine-grained access uses `@PreAuthorize` annotations in service or controller methods.
- Roles: `ADMIN`, `OPS`, `VENDOR_ADMIN`, `COURIER`, `CUSTOMER`, `FINANCE`, `SUPPORT`.

### Errors and correlation

- Every error body is an RFC 9457 problem document built by `ApiProblems` (`common/exception`): `type/title/status/detail/instance` plus `code` (stable lowercase snake_case — clients branch on it), optional `details`, `correlationId`, `traceId`, and the legacy `message`/`timestamp`/`fieldErrors` kept for a compatibility window. Contract and consumer analysis: `docs/api/ERROR-CONTRACT.md`.
- `GlobalExceptionHandler` extends `ResponseEntityExceptionHandler`, so Spring's MVC exceptions map to proper 4xx (unknown path 404, 405, 415, malformed body/params 400) instead of the 500 catch-all. Throw `BusinessException(code, message, status)` for business errors; don't write JSON error bodies by hand — filters/interceptors that must answer directly use `ApiProblems.create(...)` (the security chain does, via `ProblemDetailSecurityHandlers`; so does `TenantRequestFilter` for `invalid_tenant_header`/`tenant_not_found`).
- `CorrelationIdFilter` runs first (`HIGHEST_PRECEDENCE`, before Spring Security): reuses an incoming `X-Correlation-Id` only if it matches `[A-Za-z0-9._:-]{1,128}`, else generates a UUID; puts it in MDC `correlationId` (a field of every log line) and the response header (CORS-exposed). `ApiProblems.traceId` is the request's W3C trace id from the MDC (see Observability).

### Rate limiting (LAC-11)

- `common/ratelimit`: Bucket4j token buckets in **Redis** (`bucket4j_jdk17-lettuce`, own Lettuce client on the `spring.data.redis.*` server, standalone only), enforced by `RateLimitInterceptor` after the security chain. Key = `rl:<group>:<METHOD> <route pattern>:<identity>` — route pattern from the handler mapping (ids in the URI never give a fresh bucket); identity = JWT `sub`, else client IP. The IP is `getRemoteAddr()`; `X-Forwarded-For` is honoured only when the peer is in `app.rate-limit.trusted-proxies` (IP/CIDR, empty by default; then the right-most non-trusted hop wins). Don't also enable `server.forward-headers-strategy`.
- Groups and limits live in `app.rate-limit.groups.*` (application.yml): `registration` (POST `/register`, `/customers/register`, 5/15 min per IP), `delivery-code` (POST `/deliveries/*/complete`, 10/5 min), `checkout` (POST, 10/min), `checkout-quote` (GET `/checkout/quote`, 30/min per account — W6-A: each call writes a `checkout_quotes` row), `uploads` (30/min), `payments` (payments/refunds/sales cancel+refund, 20/min), `provisioning` (20/min), `courier-location` (POST `/couriers/me/locations`, 30/min per courier, W5-B), `sensitive` (deliveries, dispatch, ops, tickets, admin, `/me`, 120/min), `browse` (GET catalog/search, 300/min). Overlapping groups: the most specific path pattern wins. Unlisted routes are not limited. Override per env with e.g. `APP_RATE_LIMIT_GROUPS_CHECKOUT_CAPACITY`; a changed limit applies to existing Redis buckets only once they expire (≤ one period).
- Rejection = `RateLimitedException` → 429 `rate_limited` problem document + `Retry-After` (seconds) + `details.retryAfterSeconds`. Metrics: `rate_limit_rejections_total{group}`, `rate_limit_backend_errors_total`.
- **Redis down → per-instance local buckets, not fail-open** (WARN throttled to one per 30 s + the backend-errors metric; reconnect retried at most every `reconnect-backoff`). Chosen because the limited routes include brute-force targets (PIN, registration); the trade-off is that during an outage the effective limit is N × the configured one (N instances).
- Tests run `app.rate-limit.backend=local` (`src/test/resources/config/application.yml`) with the shipped limits — test code that hammers a limited route must vary the remote address / JWT subject. `RateLimiterRedisTest` (Testcontainers) proves two contexts share one bucket; `RateLimitApiTest` covers 429/Retry-After/body.
- Out of scope for the app (LAC-11 §1/§3, external): AWS WAF managed + rate-based rules in front of `/register`, `/customers/register` and Keycloak login; CAPTCHA (Turnstile/reCAPTCHA) and `VERIFY_EMAIL` on merchant registration. Keycloak's own brute-force protection covers password login.

### Tenant model

- Tenant-scoped records carry a `tenant_id` column. **Tenant = marketplace operator** (`docs/adr/ADR-0001-tenancy-model.md`); the Pede-Aqui operator tenant is seeded by `V045` with id `5e6d0c1a-7b2f-4f3e-9c8a-0d1e2f3a4b5c` (`app.tenancy.operator-tenant-id`, env `APP_OPERATOR_TENANT_ID`). Merchants are **vendors of the operator tenant**: `POST /api/v1/register` creates a `PENDING` vendor + `VENDOR_ADMIN` profile + `merchant_users` OWNER row in the operator tenant and never a tenant (ADR-0001 step 4); new tenants come only from the M2M provisioning endpoint (`MerchantRegistrationService.provisionTenant`) or the platform console. Both onboarding flows (`MerchantRegistrationService`, `SubscriptionProvisioningService`, their controllers/DTOs and the `provisioning_requests` entity) live in the **tenant** module since W3-A (they create/look up tenants); they reach Keycloak and profiles through `auth.api.UserAccounts` and create the vendor + OWNER row through `vendor.api.MerchantOnboarding`, in the same transaction as before. Legacy per-merchant dev tenants are folded in with `backend/scripts/adr-0001-consolidate-dev-tenants.sql` (dry-run first, approval required, never a Flyway migration).
- **Merchant scope** (`merchant_users`, V049): `vendor/api/MerchantScopeGuard` is the single resolver of the vendor a `VENDOR_ADMIN`/`VENDOR_STAFF` caller is confined to — `merchant_users` first (several associations → the optional `vendor_id` JWT claim picks one, else 403), then, only while `app.merchant-scope.single-vendor-fallback-enabled=true` (default), the legacy "claim, else the tenant's single vendor" heuristic. `SalesAccessGuard`, `CatalogAccessGuard`, `InventoryService`, `SalesReportService`, `OrderService` and `OrderListingService` delegate to it; unresolved scope is always 403 `vendor_scope_unresolved`, a foreign vendor is 403 `vendor_access_denied`. Switch the flag off only when `backend/scripts/adr-0001-merchant-users-report.sql` §4 is 0 in that environment; ADR-0001 step 6 then deletes the fallback.
- `TenantContext.currentTenantId()` resolution (INC-11, SEC-06):
  - **platform admin** (`ADMIN`, no `tenant_id` claim; `isPlatformAdmin()`): the `X-Tenant-Id` header (impersonation). `TenantRequestFilter` rejects a malformed (400 `invalid_tenant_header`) or unknown (404 `tenant_not_found`) tenant and writes a `TENANT_IMPERSONATION` row to `audit_logs` for **every** request carrying the header. Cross-tenant views exist only for the platform admin **without** the header: `GET /orders`, `/orders/page`, `/orders/cursor` (`OrderListingService`) are confined to the impersonated tenant when it is sent (W3-D). `GET /admin/tenants` lists every tenant only for the platform admin; a tenant-scoped ADMIN gets a one-element array with its own tenant (`TenantService.listTenantsForCurrentAdmin`).
  - **customer-only principal** (`CUSTOMER` and no staff/merchant/courier role; `isCustomerPrincipal()`): the tenant mapped to the token's OIDC client (`azp`) in `app.tenancy.customer-clients` (`pede-aqui-web`, `pede-aqui-mobile` → operator). Unmapped client, or a `tenant_id` claim that disagrees → no tenant. Never from the header.
  - **everyone else** (OPS, FINANCE, SUPPORT, VENDOR_*, COURIER, tenant-scoped ADMIN): the JWT `tenant_id` claim only. **`X-Tenant-Id` is ignored for anyone but the platform admin**; when an anonymous caller sends it, or a non-admin sends a tenant different from its own claim, `TenantRequestFilter` logs a `SECURITY ignored X-Tenant-Id …` WARN (method + path only, no PII).
  - No resolvable tenant → services answer 403 `tenant_required`. Startup fails if the operator tenant or a mapped customer tenant does not exist.
- Public storefront endpoints (categories, vendor products, vendor search) use `TenantContext.browseTenantId()`: customers browse like anonymous visitors (ACTIVE products, cross-tenant). Marked for removal (ADR-0001 step 6, `TODO(ADR-0001 step 6)` in `TenantContext`): once the dev tenants are consolidated and the fallback flag is off, browsing is confined to the tenant mapped to the client/host — see `docs/api/API-MIGRATION.md`.
- **Customer profile**: `CustomerProfileProvisioningService` creates the `AppUserProfile` (role `CUSTOMER`) idempotently (`INSERT … ON CONFLICT (tenant_id, keycloak_user_id) DO NOTHING`) at `POST /customers/register` (operator tenant) and, as a safety net, on every authenticated customer request (`TenantRequestFilter`). So register → login → cart → checkout works with no tenant header.
- Realm: seed `ops`/`finance`/`support` carry `tenant_id` = operator tenant; only `admin` is a platform admin. `tenant_id` is declared in the realm user profile with admin-only view/edit — Keycloak 26 otherwise silently drops it when set via the Admin REST API, and users must never be able to edit it.
- Service methods validate tenant context; repositories are plain Spring Data JPA interfaces.

### Database

- Migrations live in `backend/src/main/resources/db/migration/` as Flyway `V<NNN>__<name>.sql`. (A local `backend/backend/` is a stray, git-ignored build-artifact dir, not the module.)
- `ddl-auto: validate` — Hibernate never mutates schema; always create a migration for schema changes.
- PostGIS extension enabled (used for geo/zone features). `customer_addresses.location` is `geography(Point,4326)` (V046, INC-12 expand phase): the app still writes `latitude`/`longitude` and a DB trigger derives `location`; the contract step (drop lat/lng) is pending.
- `vendors.location` (`geography(Point,4326)`) and `zones.area` (`geography(MultiPolygon,4326)`) arrived in V062 (LAC-39 expand phase, same pattern): the app still writes `vendors.latitude/longitude` and `zones.geometry_wkt`, and BEFORE triggers derive the geography columns (unmapped in JPA — never write them from Java). Unusable input yields NULL, never an error: vendor coordinates missing/half-set/(0,0)/out of range → `location` NULL; WKT that is not a valid (`ST_IsValid`) POLYGON/MULTIPOLYGON in SRID 4326 (`zones_area_from_wkt`) → `area` NULL. Both have GiST indexes. Report queries for rows needing correction are in V062's header. Contract (drop lat/lng/WKT once the zone editor, LAC-60, writes `area`) is a later package. There is no `vendor_zones` table: a store's delivery zone is `vendors.delivery_zone_id` (V016).
- Referential integrity (LAC-58, V050/V051): `customer_id` columns (orders, carts, customer_addresses, promotion_redemption) reference `app_user_profiles(id)` — the profile id, not the Keycloak subject — and every `vendor_id`, `courier_id`, `cart_id`, `category_id`, `operating_zone_id`, promotion target and `verticals.tenant_id` has a validated FK (`fk_<table>_<column>`, ON DELETE NO ACTION). Deliberately without FK: `orders.delivery_address_id` (address snapshot), `orders.quote_*_id` (historical quote ids), `customer_favorite_vendors.customer_id` (stores the Keycloak sub), `ratings.rater_user_id`, and the VARCHAR user ids in `audit_logs`/`support_tickets`. SQL-seeded tests must insert real parents (`common/TestParents` in tests) and delete children before parents. New FKs on existing tables: add `NOT VALID` in one migration (with an orphan report in its header) and `VALIDATE CONSTRAINT` in the next.
- SKU codes are unique per **(tenant, vendor, sku_code)** (`uq_skus_tenant_vendor_code`, V056, LAC-16): two stores of the operator may share a code; a repeat within one vendor → 409 `sku_code_conflict`. `skus.vendor_id` is derived from `products.vendor_id` by trigger (`trg_skus_derive_vendor_id`, kept in sync by `trg_products_propagate_vendor_id`) and mapped read-only on `Sku` — never write it from code; SQL-seeded tests may omit it.
- Customer phone (V063, LAC-18): `app_user_profiles.phone_e164` (E.164 `CHECK`, unique per tenant via partial index `uq_app_user_profiles_tenant_phone_e164`, nullable) + `phone_verified_at`, written only by `CustomerProfileProvisioningService.syncVerifiedPhone` (mapped read-only on `AppUserProfile`). The old free-text `phone` column is unrelated and unverified.
- `audit_logs` is **append-only** (V053 trigger: UPDATE/DELETE/TRUNCATE fail with 42501; `AuditLog` is `@Immutable`). Never clean audit rows in tests or scripts — seed fresh tenants instead. The only sanctioned delete is a future retention job (24 months, LAC-63; not implemented) running `SET LOCAL app.audit_logs_purge = 'on'` in its transaction.
- Courier status and GPS (W5-B, V060/V061): `couriers.status` (`OFFLINE|AVAILABLE|BUSY|SUSPENDED`, CHECK) is the operational state; `couriers.available` is **deprecated** and derived from it by the trigger `trg_couriers_sync_status` (= `AVAILABLE` or `BUSY`), which also maps a write that only toggles `available` (pre-V060 code, legacy SQL seeds) onto the status — so SQL seeds may still insert `available = TRUE` (→ `AVAILABLE`). `vehicle_type` is an enum (`MOTORBIKE|BICYCLE|CAR|ON_FOOT|OTHER`, CHECK; V060 mapped the old free text by prefix, unknown → `OTHER`). `max_active_deliveries` is fixed at 1 (CHECK) because V035 `uq_deliveries_active_courier` allows one active delivery per courier — raising it needs a migration that replaces that index. `courier_last_locations` (PK courier, `geography(Point)` + lat/lng, `received_at` = presence) and `courier_location_history` (plain table + BRIN on `received_at`, 30-day retention; not partitioned on purpose — see the V061 header) are written through JDBC (`dispatch/repository/CourierLocationRepository`); tests seeding them must delete history/last-location rows before couriers/deliveries.
- Settlement ledger (V065/V066, W6-B, ADR-0005 *Proposed*): `ledger_accounts` / `ledger_transactions` (idempotency key UNIQUE per tenant) / `ledger_entries` (`NUMERIC(14,2)`, currency CHECK `'MZN'`, debit **or** credit > 0) are **append-only** (UPDATE/DELETE/TRUNCATE → 42501, no purge escape; accounts allow only a `name` update) and a `DEFERRABLE INITIALLY DEFERRED` constraint trigger rejects at COMMIT any transaction whose Σ debit ≠ Σ credit or that has no lines (23514). Written only through JDBC by `settlement` (`LedgerRepository`, never JPA). No FKs to tenants/orders/vendors on purpose (values, like `audit_logs`); never clean ledger rows in tests — seed fresh tenants. Balances are derived (`ledger_account_balances` view). `commission_plans` + `vendor_commission_overrides` (V066) hold commission rates; `commissions` (V008) is now written by settlement (`uq_commissions_tenant_order`, new columns `plan_id`, `currency`, `source`, `ledger_transaction_id`); `fee_policies.commission_rate` is unused.
- Infrastructure tables (V052): `event_publication` (Spring Modulith JDBC event registry — rows without `completion_date` are undelivered events) and `shedlock` (one row per job name). Both are Flyway-owned; never let a library auto-create schema.

### Pagination (LAC-14)

- No unbounded list queries: never `findAll()` / `findByTenantId(...)` returning a `List` for an endpoint. Shared helpers in `common/pagination`: `PageLimits` (legacy cap 200, cursor limit 1..200 default 50, page size 1..100 default 20, `NEWEST_FIRST` = `createdAt DESC, id DESC`), `KeysetCursor`, `CursorPage` (`{items, nextCursor}`), `PageResponse` (`{content, page, size, totalElements}`), `CappedList`.
- Large/append-only lists (audit, notifications, orders) get a **keyset** endpoint (`…/cursor?limit=&cursor=`): repository query `WHERE <scope> AND (created_at < :c OR (created_at = :c AND id < :id)) ORDER BY created_at DESC, id DESC` fetched with `PageLimits.keysetProbe(limit)` (limit+1). Smaller admin lists get an **offset** `…/page?page=&size=` endpoint via `PageLimits.page(...)`.
- Existing array endpoints keep their shape for the frontends but return `CappedList` → `ResponseEntity` with the newest 200 rows and `X-Truncated: true` when capped. New list endpoints should be paged from the start. Each new ordering needs a `(tenant_id, …, created_at DESC, id DESC)` index (see V054). Contract details: `docs/api/API-MIGRATION.md` (W2-B).

### Caching

- Spring Cache on Redis (`spring.cache.type: ${CACHE_TYPE:redis}`; JSON serialization and TTLs in `common/config/RedisConfig`). Only cache today: `vendorSearch` (LAC-51), TTL 60 s, so store/product changes surface in search within a minute.
- Service areas (LAC-39): `geo.api.ServiceArea.covers(tenantId, zoneId, point)` / `covers(tenantId, point)` evaluate `ST_Covers(zones.area, point)` over ACTIVE zones (boundary covered; zones with NULL `area` cover nothing — fail closed). Checkout uses `coverage(tenantId, zoneId, point)` (W6-A, see Checkout v2): zones **without** a polygon are UNRESTRICTED there (allowed), unlike `covers`.
- `@Cacheable` only works across a Spring proxy: never put it on a private or self-invoked method. The search cache lives in its own bean, `geo/service/VendorSearchCache`; `SearchService` calls it with a `VendorSearchQuery` whose `cacheKey()` holds every filter, the browse tenant (`*` = cross-tenant) and coordinates rounded to 3 decimals (~100 m — the search itself runs on the rounded point). The full filtered list is cached once; pages and `totalCount` are cut from it. Add any new filter to `VendorSearchQuery` or results will leak between queries.
- Cache errors are logged and ignored (`LoggingCacheErrorHandler`): with Redis down the search runs uncached. The test suite runs with `spring.cache.type=none` (`src/test/resources/config/application.yml`); `VendorSearchCacheRedisTest` covers the real Redis round-trip and TTL.

### Storage

Profile-driven: **dev = MinIO** (default), **prod = AWS S3**. Pattern: call `/uploads/images/presigned-url` or `/uploads/documents/presigned-url` with `{ contentType, purpose, fileName, contentLength }` to get `{ uploadUrl, storageKey, expiresInSeconds, maxBytes }`, then PUT the file directly to `uploadUrl` with that exact `Content-Type` (the body length must equal `contentLength`). Pass `storageKey` back to the API to link the file to an entity.

- **Upload limits (LAC-12).** Both presign endpoints require `ADMIN`/`OPS`/`VENDOR_ADMIN`/`VENDOR_STAFF`/`COURIER`. `contentLength` above `app.storage.max-image-bytes` (5 MB) / `max-document-bytes` (10 MB) → 400 `upload_too_large`. Content-Type and Content-Length are **signed headers** of the presigned PUT, so S3/MinIO answer 403 to a body of another size or type (AWS SDK v2 has no presigned POST/`content-length-range`, hence this design). On link, `upload/service/StoredUploadValidator` checks the key is in the caller tenant's namespace (`tenants/{tenant}/uploads/` for images, `/documents/` for documents) and runs `HeadObject` (exists, size, type) — used by product create/set-image, vendor logo (create, or update when the key changes), vendor/courier documents and delivery proof photos. Errors: 400 `invalid_storage_key` / `upload_not_found` / `upload_too_large` / `invalid_content_type`, 503 `storage_unavailable`. Verified against the compose MinIO image by `MinioUploadLimitsIntegrationTest`. Not done yet: async resize/EXIF strip and antivirus.

- Presigner is `S3Config` reading `app.storage.*`. A non-empty `s3-endpoint` switches to MinIO/path-style; empty targets real AWS. Explicit access keys win over the AWS default chain.
- **`dev` profile** (`application-dev.yml`, active by default): MinIO at `http://localhost:9000`, bucket `pede-aqui-uploads`, `minioadmin` creds — all hardcoded defaults, overridable via `MINIO_*` vars. The bucket is auto-created by the `minio-init` compose service. MinIO answers CORS `*` by default, so browser uploads need no extra config. The `AWS_*` vars in `.env` are ignored for storage in dev.
- **`prod` profile** (`application-prod.yml`): real S3; `AWS_S3_BUCKET`/`AWS_REGION` have no defaults so startup fails fast if unset. Leave access keys unset in prod when an instance role exists — the default chain picks it up.
- Presigning is pure local crypto (no network call), which is why the compose backend signs `localhost:9000` URLs it can't itself reach — the browser on the host does the PUT.
- `application.yml` auto-imports the repo-root `.env` via `spring.config.import` — but a real OS env var still overrides the `.env` value. A stale backend process on port 8080 is the usual reason config changes "don't take"; kill it (`lsof -i :8080`) before restarting.
- **Browser-direct uploads to real S3 need bucket CORS.** A presigned URL authorizes the PUT but the browser preflight still fails unless the bucket has a CORS policy allowing the app origin. This is the whole reason the Terraform exists. (MinIO doesn't have this problem.)
- **AWS state (2026-07): the dev bucket `pede-aqui-dev-documents-*` was deleted.** `infra/terraform.tfvars` now has `manage_bucket = true` so one `terraform apply` recreates bucket + public-access-block + ownership + CORS — but it requires `s3:CreateBucket`, and **neither local AWS profile has it**: both `default` (`tms-springboot-dev`) and `admin` (`delivery-springboot-dev` — misleading name, it's an app user) are object-rw only. Recreating the bucket needs real admin credentials added to `~/.aws` first.
- **Terraform is split into two root modules — this split is deliberate, don't merge them:**
  - `infra/` is **fully static — no data-source read of the bucket.** Bucket name/ARN/region are hardcoded in `infra/locals.tf` (S3 ARNs carry no account/region, so the ARN derives from the name). This lets `plan` run under a low-privilege identity that can't read the bucket.
  - `admin/` is the privileged bootstrap module (bucket-metadata read + IAM user creation). Run it with an admin profile (`terraform apply -var aws_profile=<admin>`) only when provisioning a new environment.
- **Identities:** the backend app users hold only `s3:PutObject`/`GetObject`/`DeleteObject` — no IAM permissions, no `s3:PutBucketCORS`, no `s3:CreateBucket`. Bucket-level actions are one-time privileged operations: an admin runs `terraform apply` in `infra/`, or sets CORS directly in the S3 console.

### Auth flow

BFF pattern (LAC-10) — **the browser never sees a token**:

- `src/auth.ts`: Auth.js (`next-auth@5.0.0-beta.32`, pinned) with the Keycloak provider on `delivery-app` — Authorization Code + PKCE S256 + state (`checks: ["pkce","state"]`), public client (`token_endpoint_auth_method: none`). JWT session strategy: a JWE in the HttpOnly, SameSite=Lax session cookie (`__Secure-` + Secure when `AUTH_URL` is https or `NODE_ENV=production`), 10 h max. Access/refresh/id tokens live **only inside that encrypted cookie**; the `session` callback (served to the browser by `/api/auth/session`) carries `sub`, `roles` (realm roles filtered to the marketplace ones), `tenantId` — never tokens. Expired access tokens are refreshed in the `jwt` callback with rotation, single-flight per refresh token (`lib/auth/keycloak.ts`, map on `globalThis`, completed results reused for 30 s because the realm has `refreshTokenMaxReuse: 0`); a failed refresh sets `error: "RefreshTokenError"` → 401 → login.
- `/login` is a server component whose button runs a server action `signIn("keycloak")`; Keycloak renders the login (and TOTP for ADMIN/FINANCE/OPS). Sign-out is `POST /api/session/logout` (form post, `logout()` in `lib/auth/client.ts`): clears the session + impersonation cookies and 303s to Keycloak's end_session_endpoint with `id_token_hint` and `post_logout_redirect_uri=<AUTH_URL>/login?logged_out=1`.
- `/api/bff/[...path]` proxies to `API_BASE_URL` adding `Authorization: Bearer` server-side (and `X-Tenant-Id` for an impersonating platform admin). Only `POST /register` passes without a session. Mutations must carry a same-origin `Origin` header. Backend 401 / no session → 401; `lib/http-client.ts` then redirects to `/login?expired=1&callbackUrl=…`. `lib/api/client.ts` and the CSV export (`reportsService.downloadExport`) go through it; nothing reads `sessionStorage`/cookies any more.
- Server code gets the token via `withAuth()` (`lib/auth/server.ts`): it wraps `auth(handler)` (which re-issues the rotated cookie on the response) and reads the token the jwt callback published into an `AsyncLocalStorage` slot (`lib/auth/token-store.ts`). Don't copy tokens into the session to "make it easier".
- `middleware.ts` (edge) only **decrypts** the session cookie (`getToken`, no refresh) and enforces `ROUTE_RULES` in `lib/auth/roles.ts` — the route table above, any-of-roles, `/platform` = platform admin only. No session → `/login?callbackUrl=`; wrong role → `/403` (HTTP 403). `AppShell` nav uses the same table. `/screens` 404s in production builds unless `NEXT_PUBLIC_ENABLE_SCREENS=true`.
- `AppProviders` rehydrates Redux from `GET /api/session` (identity, `roles`, `role` = most privileged, impersonated tenant). `auth-slice` holds no token.

Platform super-admins "enter" a tenant with `useTenantSwitch().enter()` (`lib/auth/client.ts`): `PUT /api/session/tenant` stores it in the `pa_active_tenant` HttpOnly cookie, HMAC-signed with `AUTH_SECRET` and bound to the admin's `sub` (only platform admins may set it; a forged/foreign cookie is ignored), then `queryClient.clear()` and the Redux mirror. `exit()` does `DELETE`. The BFF forwards it as `X-Tenant-Id` only for a platform admin; the backend still enforces `isPlatformAdmin` and audits. Tenant users send no `X-Tenant-Id` (the JWT claim decides). Security headers (CSP, HSTS in prod, `frame-ancestors 'none'`, X-Frame-Options, Referrer-Policy, Permissions-Policy) are in `next.config.mjs`.

### Auth flow

Authorization Code + PKCE (S256) via `oidc-client-ts` is the **only** login path (LAC-10/W4-C); ROPC is gone from the code and refused by the realm (`pede-aqui-web.directAccessGrantsEnabled=false`). Credentials are only ever typed on the Keycloak login page.
- `src/features/auth/oidcConfig.ts` — `userManager`; `userStore` is `InMemoryWebStorage` (**tokens live only in memory** — never sessionStorage/localStorage/cookies, never Redux). Only the transient PKCE sign-in state (code_verifier/state, deleted after the callback) is in sessionStorage. `automaticSilentRenew` is off on purpose.
- `src/features/auth/session.ts` (+ singleton `authSession.ts`) — `renew()` is **single-flight** (refresh tokens rotate; parallel refreshes would kill the session) and, if the refresh token was rotated away by another tab (same Keycloak client session), falls back once to the SSO iframe, `getAccessToken()` (renews if expired), `restore()`, `login(redirect, loginHint?)` (redirect target restricted to same-app paths by `safeRedirect`).
- Reload: tokens are not persisted, so `initAuth` restores via `signinSilent()` → hidden iframe `prompt=none` against the Keycloak SSO cookie (`/auth/silent-callback`). While logged in, renewal uses the refresh token (triggered ~60 s before expiry by `accessTokenExpiring`, by an expired token in the request interceptor, or by a 401 — all through the same single-flight `renew`).
- Logout (`features/auth/logout.ts`): clears Redux + in-memory user and calls Keycloak end-session with `id_token_hint` (post-logout redirect `/`); without end-session the silent restore would log the user straight back in.
- `ProtectedRoute` sends anonymous users to `/login?redirect=…`; a lost session (401 after one renewal) calls `authSession.login(currentPath)` directly.

Customer registration hits the backend at `POST /api/v1/customers/register` (open endpoint), which creates a Keycloak user via `KeycloakAdminService.createCustomer()`, assigns the `CUSTOMER` role and provisions the customer profile in the operator tenant. The web client never sends `X-Tenant-Id`: the backend derives the customer's tenant from the `pede-aqui-web` client (`azp`).

## Key API Flows

- **Product lifecycle**: products are created `PENDING` and only become visible after admin approval (`Product.approve()` → `ACTIVE`). Approve/reject is OPS/ADMIN only and audited (`PRODUCT_APPROVED`/`PRODUCT_REJECTED`). `CartService.addItem` refuses a SKU whose product is not `ACTIVE` (409 `product_not_available`) or an inactive SKU (409 `sku_inactive`). It also refuses a SKU of a vendor other than the request's `vendorId` (422 `sku_vendor_mismatch`).
- **Catalog/stock authorization (INC-05)**: product/SKU create and variation group/option writes require VENDOR_ADMIN/OPS/ADMIN; category and vertical create/update/delete require OPS/ADMIN (LAC-06); VENDOR_ADMIN/VENDOR_STAFF are confined to their own vendor via `CatalogAccessGuard` → `MerchantScopeGuard` (product/SKU/variation resolve to the product's vendor; `createProduct` also requires the vendor to exist in the tenant). Categories are tenant-wide (with tenant = operator, every merchant shares them), so VENDOR_ADMIN only reads them; `/catalogo/categorias` and `/catalogo/verticais` hide their write actions unless the role is OPS/ADMIN. `PATCH /inventory/{id}/stock` requires VENDOR_ADMIN/VENDOR_STAFF of the owning vendor, OPS or ADMIN (checked in `InventoryService` with `MerchantScopeGuard` directly — same ADMIN/OPS rule as `CatalogAccessGuard`, deliberately not `hasTenantWideRole()` which adds FINANCE), is tenant-scoped (other tenant → 404) and audited (`INVENTORY_STOCK_UPDATED`). Vendor search (`/search/vendors`) derives its vendor list from products with status `ACTIVE` — an empty storefront usually means no ACTIVE products, not a broken endpoint. With `lat`/`lng` (LAC-39) the candidates come from one PostGIS query (`geo/repository/VendorProximityRepository.WITHIN_RADIUS_SQL`: `ST_DWithin(vendors.location, point, radius)` on the GiST index + `ST_Distance` on geography, nearest first): vendors without a `location` are **excluded**; without `lat`/`lng` no radius applies and `distanceKm`/`distanceMeters` are null. That proximity query is plain SQL in geo on purpose (a geo dependency on vendor's repository types would be a new ModularityTest violation). Name and rating come from the vendor row.
- **Pricing (INC-13)**: one engine, `cart/service/PricingService`, prices cart, checkout, `GET /cart/pricing` and vendor search (`common/pricing/*` value types; vendor search reaches it through the `geo.api.DeliveryFeeEstimator` interface the engine implements, so geo does not depend on cart). Inputs: the tenant's `fee_policies` row (delivery base fee, flat `service_fee` + `service_fee_rate` × subtotal, `tax_rate` = standard VAT rate, `tax_inclusive`; `version` = `@Version`) and the vendor's active `delivery_fee_rules` bands, matched on a server-side PostGIS straight-line distance (`VendorRepository.straightLineDistancesKm`, `vendors.location` → address snapshot / search position). Fallbacks, never zero for a non-empty cart: no coordinates on either side or no rules → `POLICY_BASE` (fee_policies.delivery_fee); tenant without a policy → `PLATFORM_DEFAULT` (5.00 / 5 % / VAT 16 % included, same as the V048 seed after V064). Bands are inclusive; gaps/beyond the last band use the nearest lower band. Cart fees are an address-less estimate; checkout re-quotes with the address and stores the applied quote in immutable `orders.quote_*` (V048: amounts, rates, basis, distance, policy/rule ids + versions). `GET /api/v1/checkout/quote?cartId&addressId` returns exactly what checkout will charge. Money is `BigDecimal` only (ADR-0003); the `MVP10` magic coupon is gone — coupons/promotions are spec-002 (`POST /cart/{id}/coupon`, `marketing.api.CheckoutDiscountResolver` evaluated against `marketing.api.PromotionBasket`, which the `Cart` entity implements), applied on top of the quote.
- **VAT (W6-A, LAC-22) — fiscal assumptions "a validar com contabilista" (LAC-38)**: IVA 16 % (Moçambique); catalogue prices and platform fees (delivery, service) are **VAT-inclusive** (B2C); VAT is **extracted**, never added: `vat = gross × rate / (1 + rate)` per goods line and per fee, HALF_UP 2 dp, then summed (`common/pricing/VatBreakdown`); a discount is allocated to the goods tax categories pro rata (remainder to the last) and removes the VAT it contains (excess over goods reduces the fees VAT); the platform is a collection agent (merchant = seller, VAT on goods is the merchant's; in the ledger goods VAT stays in `MERCHANT_PAYABLE` and the stored `quote_fees_vat` goes to `PLATFORM_VAT_PAYABLE` — see Settlement ledger). Engine `pricing-v2`: with `fee_policies.tax_inclusive` (default true) the `taxes` line is **0** and `total = subtotal + fees − discount`; `tax_inclusive=false` keeps the pre-W6-A formula (`taxes = subtotal × tax_rate` added). V064 changed every `tax_rate = 0.08` row to 0.16 (seeded/admin-set rows are indistinguishable). Per-product `products.tax_category` (`STANDARD` default; `ZERO`/`EXEMPT` = 0 % for future use, no API yet). The order stores the VAT of the charged total in immutable `orders.quote_vat_total/quote_net_total/quote_goods_vat/quote_fees_vat/quote_goods_{standard,zero,exempt}_gross/quote_tax_inclusive` and per line `order_items.tax_category/vat_rate/vat_amount` (pre-discount); pre-W6-A orders have NULLs and their VAT is `orders.taxes`. Sales reports expose `vatIncluded` (`COALESCE(quote_vat_total, taxes)`) and `grossExVat`. Characterization (old → new totals): `CheckoutTotalsW6aCharacterizationTest`.
- **Checkout v2 (W6-A)**: `GET /checkout/quote` stores a `checkout_quotes` row (rate-limit group `checkout-quote`, 30/min; TTL `app.checkout.quote-ttl`, default 10 min; purged by job `checkout-quote-cleanup`) and returns `quoteId`/`expiresAt` + `vatIncluded`/`goodsVat`/`feesVat`/`netTotal`. `POST /checkout` with optional `quoteId` (owner-scoped `CheckoutQuoteStore`, else 404; other cart/address → 422 `quote_mismatch`) charges exactly that quote or answers **409 `quote_changed`** (`details.reason` = `expired`/`amounts_changed`/`prices_changed`, `details.quote` = fresh quote built in a new transaction after the rollback); only subtotal/delivery/service/taxes are compared — the discount is re-resolved as before (no compare → no loop with automatic promotions). Without `quoteId` behaviour is unchanged (`price_changed`). `order/service/DeliveryAreaPolicy` (quote + checkout, with an address): vendor `delivery_zone_id` polygon must cover the address (`ServiceArea.coverage`) → else 422 `out_of_service_area` — **allowed** when the vendor has no zone, the zone has no polygon, or the address has no coordinates; a non-`ACTIVE` zone serves nobody; straight-line distance above `vendors.max_delivery_distance_km` (else `fee_policies.max_delivery_distance_km`; both NULL = no limit, default) → 422 `address_too_far`. Readiness to close the legacy no-address window: these checks only run with an address, so closing `app.checkout.legacy-without-address-enabled` (separate decision, not done) makes them mandatory.
- **Checkout**: cart → checkout (idempotency key) → mock payment → delivery record — all in one transaction (`OrderService.checkout` drives it with a `TransactionTemplate`, so it is deliberately not `@Transactional`). The order starts `PAYMENT_PENDING` with a `PENDING_CONFIRMATION` payment. Idempotency (INC-07): the cart row is locked `FOR UPDATE` and the key re-read, so duplicate submits return the first order (**201 on create, 200 on replay**); a concurrent loser that hits `uq_orders_tenant_checkout_key` rolls back and re-reads the winner in a fresh transaction. The key is bound to customer + cart (`orders.cart_id`): reuse with another cart/customer → 409 `idempotency_key_reused`. Each line is revalidated at checkout — inactive SKU → 409 `sku_inactive`, non-ACTIVE product → 409 `product_not_available`, price ≠ cart snapshot → 409 `price_changed` with `details.items[{skuId, previousUnitPrice, currentUnitPrice}]`; on `price_changed` the cart is re-priced so the customer reviews and resubmits. **Delivery address (INC-12)**: the request carries `addressId` (a saved address of the caller, managed via `GET/POST/PUT/DELETE /customers/me/addresses`; another customer's → 404); it is copied into an immutable `orders.delivery_*` snapshot (V047, `DeliveryAddressSnapshot`, insert-only + DB trigger). Requests without `addressId` are a deprecated legacy shape accepted while `app.checkout.legacy-without-address-enabled=true` (response `Deprecation: true`, no snapshot); `false` → 400 `address_required` — window in `docs/api/API-MIGRATION.md`. Address exposure: the order's customer gets `OrderResponse.deliveryAddress`; the assigned courier reads `GET /deliveries/{id}/address` only from `ACCEPTED` to `ARRIVED_AT_CUSTOMER`; vendors/ops get only `AdminOrderResponse.deliveryArea` (city).
- **Stock lifecycle (INC-07)**: `reserve` moves units `available → reserved` at checkout. `orders.stock_status` (`RESERVED → RELEASED | COMMITTED`) makes the rest exactly-once via `OrderStockService`: release on sales cancel / override-cancel / vendor rejection / failed delivery before pickup, and on a **full refund approval before pickup** (`PaymentService.approveRefund` when the payment reaches `FULLY_REFUNDED`: released unless the goods left the store — delivery in `DeliveryStatus.isGoodsLeftTheStore()` = `PICKED_UP`/`ON_ROUTE_TO_CUSTOMER`/`ARRIVED_AT_CUSTOMER`/`DELIVERED`/`FAILED_DELIVERY`, or order status `PICKED_UP`/`DELIVERING`/`DELIVERED` for rows without a delivery; same classification as the V043 data fix; an engaged-but-not-picked-up courier does not block the release — that delivery is retired, see Delivery completion); commit (drains `reserved` only — on-hand = available + reserved) on courier `PICKED_UP`, on PIN completion (`DeliveryService.complete`) because the courier app may complete straight from `ACCEPTED` without a `PICKED_UP` PATCH, and on the ops status override `DELIVERING → DELIVERED` (`SalesService.statusOverride`) — all no-ops if already committed. Inventory rows are locked `FOR UPDATE` in SKU order. **Safety net (LAC-23):** `ReservationReconciler` (job `reservation-reconciler`, every 15 min, batch 200, orders untouched for `grace-period` 10 min) finds orders still `RESERVED` that are terminal or whose goods left the store and applies the same release/commit with the V043 classification (`ReservationReconciler.classify`); a `REFUNDED` order whose courier is still engaged before pickup is only logged (needs ops). Lock order: payment `FOR UPDATE SKIP LOCKED` → order + delivery re-read → inventory; every fix is a WARN `Stock drift fixed` and `stock_reconciler_orders_total{outcome=released|committed|skipped_busy|needs_attention|failed|already_settled}`. Unhandled `DataIntegrityViolationException` → 409 `conflict`, `@Version` conflicts → 409 `concurrent_modification` (no constraint names exposed).
- **Mock payment confirmation** (`POST /payments/{id}/confirm`, body `{ idempotencyKey }` = the payment's key, i.e. the checkout key) is a **development-only** feature gated by `app.payments.mock-confirmation.enabled` (`false` in `application.yml`, `true` only in `application-dev.yml`). Disabled → `404` for every caller. Enabled → only the customer who owns the order (other customers get `404`) or `OPS`/`ADMIN` (other roles `403`); only a `PENDING_CONFIRMATION` payment of a `PAYMENT_PENDING` order advances (else `409 payment_not_confirmable`), and a repeat returns the same confirmed result without a second audit log. The endpoint deliberately has no `@PreAuthorize` (so "disabled" can be 404 for all roles) — checks live in `PaymentService.confirm`. Production confirmation must come only from a PSP webhook/status query (FR-030/FR-032, not built yet).
- **Delivery completion** (`POST /deliveries/{id}/complete`, `DeliveryService.complete`): only the **assigned courier** (caller's profile → courier in tenant must equal `delivery.courierId`; OPS/ADMIN cannot complete with the PIN) submits the customer's 6-digit PIN, and only from `ARRIVED_AT_CUSTOMER` or `ACCEPTED` (the courier app posts `/complete` straight after accepting the job — narrow to `ARRIVED_AT_CUSTOMER` once the app PATCHes intermediate statuses). Already `DELIVERED` → 409, other states → 409. **The order must still be deliverable**: if it is `REFUNDED`, `CANCELLED` or legacy `REJECTED_BY_VENDOR`, both `/complete` and `PATCH /status` (courier and OPS/ADMIN) answer 409 `order_not_deliverable` — checked after ownership (403/404) and the delivery-state 409s, before the lockout (423) and the PIN compare, so a refused call has no side effect (no counter, event, audit or stock movement). `REFUND_PENDING` is not in the set (never written; a pending refund may still be rejected). A wrong PIN commits only the attempt counter + `CONFIRMATION_FAILED` event (`InvalidDeliveryCodeException`, `noRollbackFor`); at `app.delivery.max-code-attempts` (default 5) it locks: 423 `delivery_code_locked`, `CONFIRMATION_LOCKED` event, audit `DELIVERY_CODE_LOCKED`. OPS/ADMIN unlock via `POST /ops/deliveries/{id}/unlock-code` (audited). PIN hash is HMAC-SHA256 (`app.delivery.code-hmac-secret`), constant-time compare; rows created before V038 are flagged `confirmation_code_legacy` and also accept the old unsalted SHA-256. PINs are not unique per tenant (V037 dropped that constraint). The plain PIN (`orders.delivery_confirmation_code_display`, shown to the customer while active) is nulled when the order becomes `DELIVERED`/`CANCELLED` (incl. failed delivery and the ops status override to `DELIVERED`) and `REFUNDED` (always — no courier can complete a refunded order any more, so the REFUNDED transition clears it unconditionally — `Order.applyStatusChange`). PIN never logged. **Delivery retirement** (`delivery/api/DeliveryRetirementService.retireBeforePickup`, runs in the caller's transaction after the payment lock and order read, before inventory): a full refund (`PaymentService.approveRefund` → `FULLY_REFUNDED` → `OrderPaymentHooks.onPaymentFullyRefunded`), a sales cancel, an override to `CANCELLED` and a seller rejection move a delivery that is still before pickup (`DeliveryStatus.isRetirableBeforePickup()` = not `CANCELLED` and not `isGoodsLeftTheStore()`, i.e. `DISPATCH_PENDING`/`ASSIGNED`/`ACCEPTED`/`REJECTED`/`ARRIVED_AT_VENDOR`/`REASSIGNED`) to `CANCELLED`, cancel its active dispatch job (done by dispatch's `DispatchJobRetirement` through the `delivery.api.DeliveryRetirementListener` hook, same transaction: `DispatchService.ACTIVE_JOB_STATUSES` → `DispatchJobStatus.CANCELLED`, which frees the courier and the V035 slots) and write a `RETIRED` delivery event; idempotent. From pickup on the delivery is left alone (goods are out, stock committed) and the guard above stops the courier; ops resolve it manually (there is no ops delivery-cancel endpoint yet). A concurrent courier PATCH on the same delivery loses on the delivery `@Version` (409 `concurrent_modification`).
- **Order state machine (LAC-25, W4-A)**: `order.api.OrderStateMachine` is the only way an order changes status — `Order` has no status setters, only `applyStatusChange(OrderStateMachine.Change)`, and a `Change` can only be created by the machine. It holds the explicit table of the **current** `OrderStatus` enum (kept as is: fulfilment and payment axes are *not* split; the financial state lives on `Payment`). A transition outside the table → **409 `invalid_order_transition` before any effect**; every accepted one, in the caller's transaction, appends an `order_status_history` row and publishes `OrderStatusChanged`. Callers keep their narrower policies (lock order, idempotent repeats, sales override allow-list / cancellable set, vendor-rejection set — `SalesTransitionPolicyTest`/`OrderTransitionPolicyTest` pin them inside the table). Table (`OrderStateMachineTest`):

  | From | Allowed targets | Written by |
  |---|---|---|
  | (checkout) | `PAYMENT_PENDING` | `OrderService.createOrder` (history row `null → PAYMENT_PENDING`, no event) |
  | `PAYMENT_PENDING` | `PAYMENT_CONFIRMED`, `CANCELLED` | payment confirmation; sales cancel, `payment-expiry` job (`PAYMENT_EXPIRED`), customer cancel (`CUSTOMER_CANCELLED`) |
  | `PAYMENT_CONFIRMED` | `ACCEPTED_BY_VENDOR`, `CANCELLED`, `REFUNDED` | vendor accept; seller rejection, sales cancel/override, `acceptance-timeout` job (`VENDOR_TIMEOUT`), customer cancel (`CUSTOMER_CANCELLED`); full refund |
  | `ACCEPTED_BY_VENDOR` | `PREPARING`, `CANCELLED`, `REFUNDED` | vendor / sales override; rejection, sales cancel, approved customer request (`CUSTOMER_CANCELLED_WITH_FEE`); full refund |
  | `PREPARING` | `READY_FOR_PICKUP`, `CANCELLED`, `REFUNDED` | vendor; sales cancel, approved customer request (`CUSTOMER_CANCELLED_WITH_FEE`); full refund |
  | `READY_FOR_PICKUP` | `ASSIGNED_TO_COURIER`, `REFUNDED` | `DispatchService.assign`; full refund |
  | `ASSIGNED_TO_COURIER` | `PICKED_UP`, `DELIVERING`, `DELIVERED`, `CANCELLED`, `REFUNDED` | courier pickup / on the way / PIN completion / failed delivery; full refund |
  | `PICKED_UP` | `DELIVERING`, `DELIVERED`, `CANCELLED`, `REFUNDED` | as above |
  | `DELIVERING` | `DELIVERED`, `CANCELLED`, `REFUNDED` | PIN completion, sales override `DELIVERING → DELIVERED`; failed delivery; full refund |
  | `DELIVERED` | `REFUNDED` | full refund after delivery |
  | `CANCELLED`, `REFUNDED` | — (terminal) | |
  | legacy `PENDING` | `CANCELLED` | never written; existing rows can only be closed |
  | legacy `DISPATCH_PENDING` | `ASSIGNED_TO_COURIER`, `REFUNDED` | never written (sales override pair kept for old rows) |
  | legacy `REJECTED_BY_VENDOR`, `REFUND_PENDING` | `REFUNDED` | never written |

  The table is acyclic (no state is reached twice). Behaviour changes: vendor `accept|preparing|ready-for-pickup|reject` from a wrong status answer 409 (was 400); a full-refund approval of a never-paid (`PAYMENT_PENDING`) order is refused (409, rolls back); since W4-A `PICKED_UP`/`DELIVERING` are written — the order follows the courier through `DeliveryOrderHooks.onPickedUp` (`ASSIGNED_TO_COURIER → PICKED_UP`) and `onOutForDelivery` (delivery `ON_ROUTE_TO_CUSTOMER`/`ARRIVED_AT_CUSTOMER` → order `DELIVERING`), forward-only (an order in any other status is left alone). **Timeouts** (`OrderTimeoutService`, jobs below): `PAYMENT_PENDING` older than `app.orders.payment-timeout` (env `APP_ORDERS_PAYMENT_TIMEOUT`, default `PT20M`) → `CANCELLED`/`PAYMENT_EXPIRED`, payment `PENDING_CONFIRMATION → CANCELLED`, delivery retired, stock released, no refund, audit `ORDER_CANCELLED_PAYMENT_EXPIRED`; `PAYMENT_CONFIRMED` not accepted within `app.orders.acceptance-timeout` (env `APP_ORDERS_ACCEPTANCE_TIMEOUT`, default `PT10M`) of `payments.confirmed_at` (fallback `orders.updated_at`) → `CANCELLED`/`VENDOR_TIMEOUT` exactly like a seller rejection (delivery retired, stock released, refund of the eligible remainder with key `vendor-timeout-<orderId>`, notification `order_cancelled_vendor_timeout`, audit `ORDER_CANCELLED_VENDOR_TIMEOUT` with `refund_remaining=`). Sales reports exclude `PAYMENT_EXPIRED` cancellations (never paid). **History (LAC-15, V058)**: `order_status_history` and `payment_status_history` (`from_status` null on creation, `to_status`, `actor_type` `USER`/`SYSTEM`, `actor_id` = JWT subject or job name, `reason` = fixed code — never free text/PII, `correlation_id` = `X-Correlation-Id` or `jobRunId`, `created_at`), written in the same transaction as the change (`StatusChangeActor` resolves the actor); payment rows are written by `PaymentService` (checkout creation, confirmation, partial/full refund approval, expiry). Both tables are append-only (trigger rejects UPDATE/DELETE/TRUNCATE; DELETE only cascaded from the parent order/payment — `pg_trigger_depth() > 1` — or in a transaction with `SET LOCAL app.status_history_purge = 'on'`). Orders older than V058 have no rows before their first transition after deploy. Read: `GET /api/v1/orders/{id}/history` (ADMIN/OPS/SUPPORT tenant-wide; VENDOR_ADMIN/VENDOR_STAFF own vendor, other vendor → 404, `actorId` hidden) via `OrderHistoryService` + `payment.api.PaymentStatusHistoryReader`.
- **Vendor fulfillment state machine**: `PAYMENT_CONFIRMED → ACCEPTED_BY_VENDOR → PREPARING → READY_FOR_PICKUP` (through the order state machine above, which publishes `OrderStatusChanged` for these and every other transition — LAC-47, see Architecture Constraints). **Seller rejection is unified (one path)**: `PATCH /vendor/orders/{id}/reject` (from `PAYMENT_CONFIRMED`/`ACCEPTED_BY_VENDOR`; vendor users scoped to their own vendor → 404 otherwise; other statuses → 409 `invalid_order_transition`) locks the payment row first (`findByTenantIdAndOrderIdForUpdate`), then in one transaction sets the order `CANCELLED` with `orders.cancellation_reason = SELLER_REJECTED` (V044) and the vendor text in `rejection_reason`, releases stock (INC-07), clears the plain PIN, requests a refund of only the eligible remainder `payment.amount − Σ non-REJECTED refunds` (the full amount when nothing was refunded before; **no refund row when nothing remains**; key `seller-reject-<orderId>`, `PaymentService.requestRemainingRefund`), notifies the customer (`order_rejected`) and audits `ORDER_CANCELLED_SELLER_REJECTED` with business reference `refund_remaining=<amount>` — any failure rolls back everything. The financial state (`PARTIALLY_REFUNDED`/`FULLY_REFUNDED`) lives on the payment. Idempotent: a repeat or concurrent rejection, or a rejection of an order already `CANCELLED` by another path (ops cancel) or in the **legacy** `REJECTED_BY_VENDOR` status (rows written before the unification, with a `vendor-rejection-<orderId>` refund), returns the current order with no new refund, audit or notification. `OrderStatus.REJECTED_BY_VENDOR` is never written any more (kept for existing rows); `OrderResponse`/`AdminOrderResponse` expose `cancellationReason` so clients can still tell a seller rejection from other cancellations. The vendor dashboard "rejected" counter and the reports `cancelledCount` count `CANCELLED + SELLER_REJECTED` plus legacy `REJECTED_BY_VENDOR` rows. The transition is also in `order_status_history` (reason `SELLER_REJECTED`; the vendor text stays in `rejection_reason`/audit only).
- **Customer order history (LAC-21)**: `GET /api/v1/me/orders?limit=&cursor=` (keyset, newest first, `{items, nextCursor}`; summary = status, `cancellationReason`, totals, vendor name, item count, `createdAt`) and `GET /api/v1/me/orders/{id}` (items, delivery-address snapshot, totals + quote breakdown, `deliveryCode` = the plain PIN, which the entity clears once the order is delivered/cancelled/refunded). CUSTOMER only (`order/controller/CustomerOrderController`, read-only `CustomerOrderQueryService` + `CustomerOrderQueryRepository`; caller profile via `auth.api.UserAccounts.profileIdOf`, vendor names via `vendor.api.VendorNames`). Scope is tenant (from `azp`) + the caller's profile id inside the query, so another customer's or tenant's order is **404**. No status filter or courier info yet. The list is served by V057 `idx_orders_tenant_customer_created_id (tenant_id, customer_id, created_at DESC, id DESC)`, which replaced V003's prefix index `idx_orders_tenant_customer`.
- **Customer cancellation (LAC-26, W5-A)**: `POST /api/v1/me/orders/{id}/cancel` (CUSTOMER, own order else 404, optional `{reason}` ≤ 500) follows `order/service/CustomerCancellationPolicy` (pinned by `CustomerCancellationPolicyTest`): **free** while `PAYMENT_PENDING`/`PAYMENT_CONFIRMED` → 200, `CANCELLED` + `CUSTOMER_CANCELLED` at once (pending payment → `CANCELLED` via `PaymentService.cancelPending`; captured → refund of the eligible remainder, key `customer-cancel-<orderId>`), delivery retired, stock released, notification `order_cancelled_by_customer`, audit `ORDER_CANCELLED_BY_CUSTOMER`; **request** while `ACCEPTED_BY_VENDOR`/`PREPARING` → 202 + an open row in `cancellation_requests` (V059: status `REQUESTED|APPROVED|REJECTED`, `closure_reason` `OPS_REJECTED|ORDER_ADVANCED|ORDER_CLOSED`, quoted `fee_amount` = `app.orders.cancellation.fee-rate` (env `APP_ORDERS_CANCELLATION_FEE_RATE`, default `0.10`, validated 0..1 at startup) × subtotal HALF_UP 2 dp, one open request per order by partial unique index; the customer's text lives only there); `CANCELLED` → 200 current state; `READY_FOR_PICKUP` onwards/`REFUNDED`/legacy → 409 `order_not_cancellable`. OPS/ADMIN decide under `/api/v1/ops/cancellation-requests` (`GET ?status=&page=&size=`, `POST /{id}/approve|reject`, `OperationsCancellationRequestController`): approve → `CANCELLED` + `CUSTOMER_CANCELLED_WITH_FEE`, retire, release, refund `refundable − fee` (fee capped at what is still refundable, never negative, no refund row at 0 — `PaymentService.requestRemainingRefundLessForTenant`), notification, audit `ORDER_CANCELLATION_APPROVED`; reject → order continues (`ORDER_CANCELLATION_REJECTED`); repeats idempotent, the opposite decision → 409 `cancellation_request_closed`. An approval (or customer call) after the order moved on closes the open request (`ORDER_ADVANCED`/`ORDER_CLOSED`, audit `ORDER_CANCELLATION_REQUEST_CLOSED`) and answers 409 `order_not_cancellable` — `OrderNotCancellableException` is `noRollbackFor`, so the closure commits. There is **no** event listener closing stale requests when the vendor advances the order: the OPS list shows `orderStatus`, and the next approval closes it. Every path takes the payment lock first (lock order rule); a racing vendor accept/preparing/ready loses or wins on the order `@Version` — exactly one outcome (`CustomerCancellationPostgresTest`). `GET /me/orders/{id}` adds `cancellationPhase`, `cancellationFeeEstimate`, `cancellationRequest`; the customer web shows `OrderCancellationCard` on the order detail. The withheld fee is posted by the settlement ledger (`CANCELLATION_FEE_RETAINED`: merchant payable less commission, see Settlement ledger).
- **Vendor order scoping**: `OrderService`/`OrderListingService` use `vendor/api/MerchantScopeGuard` directly and the SUPPORT masking rule `order/api/CustomerPiiMasking` (shared with `sales/service/SalesAccessGuard`, which delegates to it; W3-A removed the order → sales dependency). Merchant users (`VENDOR_ADMIN`/`VENDOR_STAFF` without `ADMIN`/`OPS`/`FINANCE`) only list and transition their own vendor's orders; another vendor's order answers 404. The vendor comes from `merchant_users` (both roles); if nothing resolves the call fails closed with 403 `vendor_scope_unresolved`. `GET /orders` keeps its array contract; `GET /orders/page?page=&size=` is the paginated variant (max 100) — see `docs/api/API-MIGRATION.md`. All three backoffice order listings (`/orders`, `/orders/page`, `/orders/cursor`) are served by `OrderListingService` with one scoping rule; the old `OrderService.listForCurrentContext`/`listPageForCurrentContext` are no longer routed (delete them when OrderService is next touched). Two-merchant isolation (orders, products, stock, closures, sales, reports; OPS sees both) is covered end-to-end by `vendor/TwoMerchantIsolationE2ETest`.
- **Courier delivery state machine**: `ACCEPTED → ARRIVED_AT_VENDOR → PICKED_UP → ON_ROUTE_TO_CUSTOMER → ARRIVED_AT_CUSTOMER → DELIVERED | FAILED_DELIVERY` (W4-A: the order follows — dispatch offer `ASSIGNED_TO_COURIER`, pickup `PICKED_UP`, on route/arrived `DELIVERING`, completion `DELIVERED`, failure `CANCELLED`). `PATCH /deliveries/{id}/status` is limited to the assigned courier or OPS/ADMIN (audited `DELIVERY_STATUS_UPDATED`), answers 409 on invalid transitions, and cannot reach `DELIVERED` (PIN required via `/complete`). Refused with 409 `order_not_deliverable` once the order is `REFUNDED`/`CANCELLED` (see Delivery completion). `FAILED_DELIVERY` cancels the order and releases its stock if still `RESERVED` (in practice it is reachable only from `ARRIVED_AT_CUSTOMER`, after pickup committed the stock, so the release is a no-op; no refund yet).
- **Dispatch**: only `READY_FOR_PICKUP` orders; offered to the first eligible courier in `operatingZoneId` (APPROVED + `status = AVAILABLE`, LAC-42) **without an active delivery**. Reassignment excludes the prior courier. Offers expire after `app.dispatch.offer-ttl` (default 60s) — expiry only blocks acceptance, there is no automatic re-offer job yet. Only the addressed courier can accept/reject (others get 404); accept is a conditional UPDATE so concurrent accepts have one winner (409 for the rest). Exclusivity is enforced in the DB by V035 partial unique indexes (one active job per delivery: `ASSIGNED|ACCEPTED|REASSIGNABLE`; one active delivery per courier: `ASSIGNED..ARRIVED_AT_CUSTOMER`) — keep `DispatchService.ACTIVE_JOB_STATUSES` / `COURIER_BUSY_DELIVERY_STATUSES` in sync with them. Job lists are tenant-scoped, paged (`page`/`size`, max 100) and courier-scoped for COURIER.
- **Courier status (LAC-42, W5-B)**: `dispatch/service/CourierStatusService`. The courier sets only `AVAILABLE`/`OFFLINE` via `PUT /api/v1/couriers/me/status` (`PATCH /couriers/me/availability` is deprecated and maps true/false onto it): 400 `invalid_courier_status` for other values, 409 `courier_suspended`, 409 `courier_not_verified`, 409 `courier_has_active_delivery` when going offline while working an accepted delivery; going online while working one gives `BUSY`. `BUSY` is set by `DispatchService.accept` (re-reads the courier: `acceptOffer` clears the persistence context; a `SUSPENDED` courier cannot accept → 409) and cleared back to `AVAILABLE` when the delivery ends — `DeliveryService` calls the new hook `delivery.api.DeliveryCourierListener` on PIN completion and `FAILED_DELIVERY`, and `DispatchJobRetirement` calls it for retired deliveries (both optional setters, NOOP in slice tests); release only happens when no delivery in `CourierStatusService.ENGAGED_DELIVERY_STATUSES` (`ACCEPTED..ARRIVED_AT_CUSTOMER`, i.e. V035's set minus `ASSIGNED`) remains. OPS/ADMIN: `PATCH /couriers/{id}/suspend` `{reason}` (idempotent; reason stored on the row only) and `PATCH /couriers/{id}/reinstate` (→ `OFFLINE`, or `BUSY` mid-delivery; 409 `courier_not_suspended`), audited `COURIER_SUSPENDED`/`COURIER_REINSTATED`, tenant-scoped (404). Going off duty (offline, suspension, consent withdrawal, sweeper) deletes the courier's latest position (DB + Redis). Presence sweeper: see Scheduled jobs.
- **Courier GPS (LAC-40, W5-B)**: `dispatch/service/CourierLocationService`. Consent: `GET/PUT/DELETE /api/v1/couriers/me/location-consent` (COURIER) — `PUT {version}` must equal `app.courier-location.consent-version` (409 `location_consent_outdated`), stores `couriers.location_consent_accepted_at/version`, audited; bumping the configured version invalidates every consent; `DELETE` is refused mid-delivery (409 `courier_has_active_delivery`), otherwise the courier goes `OFFLINE`. Ingestion: `POST /api/v1/couriers/me/locations` `{points:[{latitude, longitude, accuracyMeters, speedMps?, headingDegrees?, recordedAt}]}` (1..50; out-of-range → 400 `validation_failed`). Gates: consent to the current version (409 `location_consent_required`), on duty = status `AVAILABLE`/`BUSY` **or** working an accepted delivery (409 `courier_off_duty`). Filters drop points (reported in `{accepted, dropped, droppedByReason}`): accuracy > 100 m `low_accuracy`, older than 5 min `too_old`, > 5 min in the future `future_timestamp`, > 120 km/h from the previous point `implausible_speed`, same instant `duplicate`. The newest accepted point upserts `courier_last_locations` (newest `recorded_at` wins; `received_at` always moves = heartbeat); route history rows are written **only while a delivery is worked** (data minimisation). Redis (`CourierPresenceStore`, after commit, failures logged/counted and ignored, off in tests via `app.courier-location.redis-enabled=false`): GEO set `couriers:geo:<tenantId>` + hash `courier:<id>:last` with TTL `presence-ttl` 2 min — a write-only fast path prepared for LAC-41; PostgreSQL is the source of truth. OPS/ADMIN: `GET /api/v1/ops/couriers/locations?zoneId=` (couriers' `operating_zone_id`, on duty only, newest 200 + `X-Truncated`, `stale` when nothing was received within the presence TTL). Coordinates are never logged. The V017 table `courier_location_updates` is unused (drop later).
- **Refunds (no PSP)**: `PaymentService.requestRefund` → `REQUESTED`; `approveRefund`/`rejectRefund` (FINANCE/ADMIN, reachable via `/payments/refunds/*` and `/finance/refunds/*`, both funnel through `PaymentService`). **Approval is an administrative record only — no money is returned to the customer; there is no PSP call.** The first approval publishes `payment.RefundApproved` (and `confirm` publishes `payment.PaymentConfirmed`) for the settlement ledger (W6-B). Lookups are tenant-scoped (another tenant's refund → 404). A request locks the payment row (`SELECT … FOR UPDATE`) and must satisfy `0 < amount ≤ payment.amount − Σ non-REJECTED refunds` (else 422); idempotency key is UNIQUE per tenant (V040) — same key returns the same refund, a key bound to another payment → 409. Financial state lives on the **payment**, independent of the order: each approval sets `Payment.status` to `PARTIALLY_REFUNDED` (approved < amount) or `FULLY_REFUNDED` (approved ≥ amount; the legacy `PaymentStatus.REFUNDED` value is never written). On full coverage the order becomes `REFUNDED` — **except a `CANCELLED` order, which stays `CANCELLED`**; a partial approval leaves the order status unchanged. Full coverage also reads the order's single delivery row (after the payment lock and the order read, before inventory) and closes what it allows: always clears the plain PIN (non-`CANCELLED` orders), and unless the goods left the store retires the delivery + its active dispatch job (see Delivery completion) and releases the stock reservation (see Stock lifecycle) — all idempotent, so an order cancelled earlier is neither retired nor released twice. After pickup the delivery is untouched; the courier then gets 409 `order_not_deliverable` on the `REFUNDED` order. Finance/dashboard gross totals sum `PaymentStatus.CAPTURED` (`CONFIRMED`, `PARTIALLY_REFUNDED`, `FULLY_REFUNDED`) and subtract refunds separately. **PSP seam (not built):** refunds are created `REQUESTED` inside the business transaction; a future PSP payout must run **after commit**, be idempotent by the refund's idempotency key, and record failures on the refund in a retryable state — a PSP failure must never roll back the order cancellation. `RefundStatus` has no `FAILED` value yet; add it with the PSP integration.
- **Settlement ledger (LAC-33/34, W6-B, ADR-0005 *Proposed* — posting model "a validar" with the accountant, LAC-38)**: the platform is a **collection agent** (merchant of record = the merchant). Module `settlement` (top of the module graph) posts double-entry transactions from events, after commit, idempotently by key: `PaymentConfirmed` → `PAYMENT_CAPTURED` (Dr `PLATFORM_CASH_CLEARING` / Cr `CUSTOMER_FUNDS_HELD`, key `payment-captured:<paymentId>`); `OrderStatusChanged` DELIVERED → `ORDER_DELIVERED` (Dr funds held P [+ Dr `PLATFORM_PROMOTION_EXPENSE` D] / Cr `PLATFORM_REVENUE_COMMISSION` C = rate × subtotal, Cr `PLATFORM_REVENUE_FEES` fees, Cr `MERCHANT_PAYABLE[vendor]` subtotal + taxes − C, key `order-delivered:<orderId>`; **VAT-inclusive orders (W6-A, `orders.quote_tax_inclusive` + `quote_fees_vat`)**: the stored fee VAT (scaled like the fees) is credited to `PLATFORM_VAT_PAYABLE` instead of `PLATFORM_REVENUE_FEES` regardless of `platform-vat-rate`, while goods VAT stays inside the merchant payable (subtotal is VAT-inclusive, taxes 0 — the merchant is the seller); orders without quote VAT keep the previous rule, plus one `commissions` row with the gross commission); `RefundApproved` → `REFUND_BEFORE_DELIVERY` (funds held → `CUSTOMER_REFUNDS_PAYABLE`) or, when approved after the DELIVERED instant, `REFUND_AFTER_DELIVERY` (proportional reversal refund/base of every delivery line, rounding residue on the merchant line), key `refund-approved:<refundId>`; `OrderStatusChanged` CANCELLED with `CUSTOMER_CANCELLED_WITH_FEE` → `CANCELLATION_FEE_RETAINED` (fee → merchant less commission). Postings read committed facts through `order.api.OrderSettlementFacts` / `payment.api.PaymentSettlementFacts` (refund before/after delivery decided by `refunds.updated_at` vs the first DELIVERED row of `order_status_history`; refunds approved before delivery scale the delivery base) and first post what they depend on (capture → delivery → refund/fee, the same order in which keys are taken; accounts are resolved in enum order first). Delivered orders without a captured payment are skipped (WARN, `ledger_postings_total{result=skipped}`). Commission rate at DELIVERED: vendor override in force → tenant default plan in force (V066 seeds 15 % per tenant) → `app.settlement.default-commission-rate` (0.15). Config `app.settlement.*`: `enabled` (env `APP_SETTLEMENT_ENABLED`, **false in the test suite**; `SettlementLedgerPostgresTest` turns it on in its own context), `platform-vat-rate` (0 = no VAT lines; > 0 treats the commission — and the fees of orders without stored quote VAT — as VAT-inclusive → `PLATFORM_VAT_PAYABLE`), `discount-funded-by` (`PLATFORM`|`MERCHANT`). Read: `GET /api/v1/finance/merchants/{vendorId}/balance` (FINANCE/ADMIN any vendor of the tenant; VENDOR_ADMIN own vendor via `MerchantScopeGuard`, else 403; unknown vendor 404) and `GET /api/v1/finance/ledger/transactions?limit=&cursor=&orderId=&vendorId=` (FINANCE/ADMIN, keyset `{items, nextCursor}` with lines). Orders older than V065 have no postings (no backfill). No payouts yet (LAC-35); `COURIER_PAYABLE` exists without postings.
- **Lock order rule (order money paths)**: any transaction that may change an order's terminal state or its refunds takes the order's **payment row `FOR UPDATE` first** (`PaymentRepository.findByTenantIdAndOrderIdForUpdate`), **then** reads the order, then the delivery/dispatch rows it retires, and only then touches inventory rows (SKU order, see Stock lifecycle). `OrderService.rejectByVendor`, `SalesService.cancel/refund/statusOverride` and `CustomerCancellationService.cancelMine/approve` all follow it (`SalesService.lockPayment`), so concurrent reject/cancel/refund calls on one order serialize and the loser sees the committed state instead of racing or deadlocking on the order row; `PaymentService.requestRefund`/`approveRefund` re-lock the same row inside the same transaction, which is re-entrant. Orders without a payment yet (pre-checkout states) have nothing to lock. When adding a new path that cancels, refunds or overrides an order, start it with the same lock.
- **Store availability (LAC-27)**: `vendor/api/StoreAvailabilityService` decides open/closed from `vendor_opening_hours` (ISO day 1=Mon…7=Sun, `[opensAt, closesAt)`, evaluated in `app.store-availability.timezone`, default `Africa/Maputo`) and `vendor_closures` (V055, `[starts_at, ends_at)`). A vendor with **no** opening-hour rows is always open; once rows exist, a missing day is closed. `vendors.available` only counts when `app.store-availability.enforce-available-flag=true` (off: the column defaults to FALSE with no UI). Enforced in `CartService.addItem` and at checkout (`CartService.requireCheckoutEligible`, called from `OrderService.createOrder` before price revalidation) → 422 `store_closed` with `details.nextOpeningAt`. Closures are managed via `GET/POST/DELETE /vendors/{id}/closures` (GET is a capped array: 200 rows, earliest first, `X-Truncated`; OPS/ADMIN; VENDOR_ADMIN own vendor via `MerchantScopeGuard`; audited `VENDOR_CLOSURE_CREATED/DELETED`). Search stamps `open`/`nextOpeningAt` **after** the `vendorSearch` cache read (never cached) and stable-sorts closed stores last.
- **Pharmacy gate (LAC-64)**: `app.verticals.pharmacy.enabled=false` by default (pending legal opinion). `catalog/api/PharmacySalePolicy` rejects products with `requires_prescription_metadata` or in a category whose `vertical` is `pharmacy` in addItem and checkout (422 `pharmacy_not_available`); with the vertical enabled, prescription products still get 422 `prescription_required` (no prescription flow). Browse/search are not filtered.
- **Audit**: sensitive admin/ops/finance actions written to `audit_logs` via `AuditLogService.log(...)` (actor, target, action, result, timestamp) plus, since LAC-15/V053, `correlation_id` (MDC), `ip` (remote address, never `X-Forwarded-For`), `user_agent` and optional `details` JSONB — secret-looking keys (pin, code, otp, password, token, secret…) are masked to `***`; still never pass PINs/secrets/tokens. Platform-level actions without a tenant context use `logForTenant(tenantId, …)`. Action names live in `common/service/AuditActions`. Order/payment status changes are additionally recorded in `order_status_history`/`payment_status_history` (W4-A, see Order state machine).

## Architecture Constraints

The backend is a layered modular monolith (ADR-0002, `docs/adr/ADR-0002-module-structure.md`). Each top-level package under `com.delivery` is a Spring Modulith (1.4.x) application module that keeps the `controller/service/repository/entity/dto/mapper` layering internally; `common` is declared an OPEN module (`common/package-info.java`). Spring Modulith is used **only** for:

- **Structural verification — no module cycles; internal accesses still baselined.** `backend/src/test/java/com/delivery/architecture/ModularityTest.java` runs `ApplicationModules.detectViolations()` and compares it with the checked-in ratchet `backend/src/test/resources/modulith/violations-baseline.txt`. Since W3-A the module graph is **acyclic** (C1–C9 and cart↔geo broken, 0 `cycle-edge` lines): any new cycle fails the build. The file now only lists `non-exposed` lines — `<module> -> <internal type of another module>` accesses that existed in 2026-10, all pointing *down* the graph (e.g. `sales`/`dashboard` reading `order`/`payment` entities). The build fails on any **new** violation and on any **stale** baseline line (a fixed violation must be deleted from the file, so the list only shrinks); when it is empty the test becomes a plain `verify()`. Regenerate only after an intentional fix: `mvn test -Dtest=ModularityTest -Dmodulith.baseline.write=true` and review the diff (it must only delete lines). Module diagrams (PlantUML) live in `docs/architecture/modules/` (`-Dmodulith.docs=true` regenerates them).
- **Module layering (W3-A, acyclic):** `settlement` (W6-B, top: → order, payment, vendor; consumes their events and `api` readers only) and main chain `dashboard`/`sales` → `dispatch` → `order` → `cart` → `tenant` → `geo` → `catalog` → `inventory` → `vendor` → `auth`/`upload`; side modules below `order`/`sales`: `payment` (→ auth), `delivery` (→ upload), `marketing` (→ catalog, vendor), `customer` (→ auth, geo), `notification` (→ auth), `finance` (→ payment); `report` → vendor. A lower module never imports a higher one. When a lower module needs a synchronous effect in a higher one **inside its own transaction** (money/lock-order paths), it declares a **hook interface in its `api` package** and the higher module implements it (Spring wires the bean): `payment.api.PaymentOrderHooks` (impl `order.service.OrderPaymentHooks`: confirmation, full-refund order/delivery/stock effects), `delivery.api.DeliveryOrderHooks` (impl `order.service.OrderDeliveryHooks`: deliverable check, DELIVERED/FAILED transitions, stock commit/release, address), `delivery.api.AssignedCourierResolver`, `delivery.api.DeliveryRetirementListener` and `delivery.api.DeliveryCourierListener` (impls `dispatch.service.CourierIdentityResolver`, `DispatchJobRetirement`, `CourierStatusService` — LAC-42 courier release), `geo.api.DeliveryFeeEstimator` (impl `cart.service.PricingService`), `marketing.api.CheckoutDiscountResolver` (impl `marketing.service.CheckoutPromotionResolver`, called by order). This is plain dependency inversion, not a command bus; use an event instead only when the reaction may run after commit. Slice tests (`@DataJpaTest` + `@Import`) must import the hook implementations their services need.
- **Transactional application events** — `ApplicationEventPublisher` inside the business transaction + `@ApplicationModuleListener` (after commit, async, own transaction) with the **JDBC** event publication registry (`spring-modulith-starter-jdbc`; table `event_publication`, created by Flyway V052, Modulith schema init disabled). Delivery is at-least-once: listeners must be idempotent. Incomplete publications are resubmitted by `EventPublicationRetryJob` (republish-on-restart is off on purpose — unsafe with several replicas); completed rows are kept 7 days (`EventPublicationCleanupJob`). Events live in the producing module's base package (public API) and are listed in `docs/architecture/EVENT-CATALOG.md` — add every new event there. Today there are three: `order.OrderStatusChanged`, published by `OrderStateMachine` for **every** order transition (W4-A), consumed by `dashboard.service.OrderStatusMetricsListener` (metric + log, no state change) and `settlement.service.SettlementEventListener` (ledger); `payment.PaymentConfirmed` and `payment.RefundApproved` (W6-B, published by `PaymentService.confirm` / first `approveRefund`), consumed only by the settlement ledger.

Modules talk to each other through their public API (base package or `@NamedInterface` `api` package) or events — never through another module's repositories or entities, and without cycles; existing exceptions are exactly the baseline file. Declared `api` named interfaces (`package-info.java` with `@NamedInterface("api")`): `vendor.api` (`MerchantScopeGuard`, `StoreAvailabilityService`, `MerchantOnboarding`, `VendorNames`), `catalog.api` (`PharmacySalePolicy`), `auth.api` (`UserAccounts`), `tenant.api` (`TenantStats`), `order.api` (`CustomerPiiMasking`, `OrderStateMachine`, `OrderSettlementFacts`), `payment.api` (`PaymentOrderHooks`, `PaymentStatusHistoryReader`, `PaymentSettlementFacts`), `delivery.api` (`DeliveryRetirementService`, `DeliveryAddressResponse`, `DeliveryOrderHooks`, `AssignedCourierResolver`, `DeliveryRetirementListener`, `DeliveryCourierListener`), `dispatch.api` (`CourierEarnings`), `marketing.api` (`CheckoutDiscountResolver`, `CheckoutDiscount`, `PromotionBasket`), `geo.api` (`DeliveryFeeEstimator`, `ServiceArea`); plus `auth.validation` (`@NamedInterface("validation")`, the `@PasswordPolicy` constraint). Put new cross-module entry points there rather than baselining the access. `PlatformController` (`/api/v1/platform/stats`) lives in `dashboard` (cross-domain reader), not `tenant`. Still avoided: DDD tactical patterns, Clean/Hexagonal Architecture, CQRS, event sourcing, command buses, Moments (excluded from the build), and Kafka/event externalization.

Every public class carries a short responsibility comment. Public service methods include short purpose comments. Business rules get comments only when non-obvious.

## Scheduled jobs (LAC-46)

- `common/jobs/JobSchedulingConfig` = `@EnableScheduling` + ShedLock (`@EnableSchedulerLock`, JDBC provider on the V052 `shedlock` table, database time). Every job is a bean with a `@Scheduled` `run()` that also carries `@SchedulerLock(name = <job>, lockAtMostFor, lockAtLeastFor)`, so it runs on **one replica** at a time, and whose body goes through `JobRunner.run(job, body)`: MDC `job`/`jobRunId` (in every log line; each run is also a traced `tasks.scheduled.execution` span), Micrometer `job_runs_total{job,result}`, `job_duration_seconds{job,result}`, `job_last_success_timestamp_seconds{job}` (alert when it stops moving), failures logged and counted, never propagated.
- Config under `app.jobs.*`: `app.jobs.enabled` (env `APP_JOBS_ENABLED`, default true) switches the scheduler off entirely; each job has `app.jobs.<job>.enabled` plus its interval/cron. **Tests run with `app.jobs.enabled=false`** (`src/test/resources/config/application.yml`): job beans still exist and tests call `run()` / the service directly.
- Jobs today: `reservation-reconciler` (15 min, see Stock lifecycle), `payment-expiry` and `acceptance-timeout` (W4-A, 1 min each, `app.jobs.<job>.enabled` / env `APP_JOBS_PAYMENT_EXPIRY_ENABLED`, `APP_JOBS_ACCEPTANCE_TIMEOUT_ENABLED`; batch `app.orders.timeout-batch-size` 200, oldest first; per order: payment `FOR UPDATE SKIP LOCKED` → order re-read/re-check → delivery retirement → inventory → refund/notification/audit; a concurrent user action either holds the payment lock (seller rejection, sales actions: the job skips) or loses/wins on the order `@Version` (vendor accept, payment confirmation: the loser rolls back entirely); metric `order_timeout_orders_total{job,outcome=cancelled|skipped_busy|already_settled|needs_attention|failed}`; covered by `OrderTimeoutPostgresTest`), `courier-presence-sweeper` (W5-B/LAC-42, 1 min, env `APP_JOBS_COURIER_PRESENCE_SWEEPER_ENABLED`; work-queue per courier with `FOR UPDATE SKIP LOCKED`: `BUSY` couriers without an accepted delivery → `AVAILABLE`; and, **only with `app.courier-presence.enforce-timeout=true`** (env `APP_COURIER_PRESENCE_ENFORCE_TIMEOUT`, default **false** until the courier app sends locations), `AVAILABLE` couriers online longer than `offline-after` 2 min with no location received since → `OFFLINE`; metric `courier_presence_sweeper_couriers_total{outcome=healed|offline|skipped_busy}`; `CourierStatusPostgresTest`), `checkout-quote-cleanup` (W6-A, daily 03:45 Africa/Maputo, env `APP_JOBS_CHECKOUT_QUOTE_CLEANUP_ENABLED`, deletes `checkout_quotes` expired more than `grace` P1D ago), `courier-location-retention` (W5-B/LAC-40, daily 04:15 Africa/Maputo, deletes `courier_location_history` received more than 30 days ago in batches of 5000, max 200 batches per run; `CourierLocationPostgresTest`), `ledger-reconciliation` (W6-B/LAC-33, daily 04:45 Africa/Maputo, env `APP_JOBS_LEDGER_RECONCILIATION_ENABLED`; read-only: tenants/transactions whose Σ debit ≠ Σ credit → ERROR log + gauges `ledger_reconciliation_imbalanced_tenants`/`_unbalanced_transactions` (alert when > 0), liability accounts with a debit balance → WARN + `ledger_reconciliation_negative_liability_accounts`), `event-publication-retry` (1 min, resubmits incomplete publications older than 5 min), `event-publication-cleanup` (daily 03:30 Africa/Maputo, deletes completed publications older than 7 days).
- **Work-queue pattern for per-item jobs** (ShedLock alone is for singleton jobs): select candidates read-only and bounded (`LIMIT`, oldest first), then handle each item in **its own transaction** that first claims it with `SELECT … FOR UPDATE SKIP LOCKED` (a row held by user traffic is skipped and retried next tick instead of blocking it), re-reads and re-checks state under the lock, and then applies the change idempotently. Follow the lock order rule for order money paths. Reference implementation: `ReservationReconciler` + `PaymentRepository.lockIdsByTenantIdAndOrderIdSkipLocked`.

## Observability (LAC-50, application part)

- **Tracing**: Micrometer Tracing + OpenTelemetry bridge + OTLP exporter (`micrometer-tracing-bridge-otel`, `opentelemetry-exporter-otlp`, versions from the Boot BOM). Pure Boot auto-config; `common/observability/ObservabilityConfig` only adds a `ContextPropagatingTaskDecorator` (async `@ApplicationModuleListener`s continue the request trace) and a `ClientRequestObservationConvention` that collapses UUID path segments to `{id}` in the outbound `uri` tag. Trace ids are always minted and put in MDC `traceId`/`spanId` (also for unsampled requests and with `TRACING_ENABLED=false`, which only stops export). Spans are **exported only when `MANAGEMENT_OTLP_TRACING_ENDPOINT` is set** (e.g. `http://otel-collector:4318/v1/traces`); never declare `management.otlp.tracing.endpoint` with an empty default/value — Boot treats empty as set and fails building the exporter. Sampling `TRACING_SAMPLING_PROBABILITY`: 0.1 by default, 1.0 in `dev`.
- **Outbound HTTP**: the `RestTemplate` bean (`common/config/RestTemplateConfig`, Keycloak admin API) is built from `RestTemplateBuilder` (simple JDK factory, as before) so calls get `http.client.requests` metrics, a client span and `traceparent`, plus the current `X-Correlation-Id`. New HTTP clients must be built from Boot's `RestTemplateBuilder`/`RestClient.Builder`, never `new RestTemplate()`. The S3 SDK is **not** instrumented (presigning is local; only `HeadObject` on link goes out).
- **Logs**: Spring Boot native structured logging, no `logback-spring.xml`. `logging.structured.format.console=${LOG_FORMAT:logstash}`, renamed to the historical fields `ts`/`msg`/`logger` + `app`; every MDC key is a top-level field (`correlationId`, `traceId`, `spanId`, `job`, `jobRunId`); stack traces are a `stack_trace` field. The `dev` profile (also the test default) logs a readable line with a `[traceId/spanId cid=… job=…/…]` block; `LOG_FORMAT=logstash` for JSON in dev.
- **Metrics**: HTTP server latency has histogram buckets (5 ms–10 s) for p95/p99. Business counters go through `common/observability/BusinessMetrics` (low-cardinality tags only — result, stable error `code` as `reason`, small enums; never ids/tenants/PII; the same tag keys on every series): `orders_checkout_total{result=created|replayed|rejected|error,reason}` (CheckoutController), `deliveries_completion_total{result,reason}` and `deliveries_status_updates_total{status,result,reason}` (DeliveryController; `status="FAILED_DELIVERY"` = failures), `uploads_rejected_total{stage=presign|link,kind,reason}` (UploadService/StoredUploadValidator), `audit_events_total{action,result}` (AuditLogService, **after commit** — payments confirmed `PAYMENT_CONFIRMED`, refunds approved `REFUND_APPROVED`, PIN lockouts `DELIVERY_CODE_LOCKED`, …), `orders_created_total` and `orders_cancelled_total{reason=seller_rejected|payment_expired|vendor_timeout|customer_cancelled|customer_cancelled_with_fee|other}` (OrderStateMachine, after commit). `courier_locations_points_total{result=accepted|dropped|batch_rejected,reason}` (CourierLocationService), `courier_presence_redis_errors_total`, `ledger_postings_total{type,result=posted|duplicate|skipped}` (settlement, own `SettlementMetrics`). Existing: `order_status_transitions_total{from,to}` (every transition since W4-A's OrderStateMachine), `job_*`, `rate_limit_*`, `stock_reconciler_orders_total`. Components take `BusinessMetrics` through an optional setter (`@Autowired(required = false)`, default `BusinessMetrics.NOOP`) so slice tests need no wiring.
- **Local stack**: `docker compose --profile observability up -d` adds OTel Collector (4317/4318) → Jaeger (UI 16686) and Grafana (3030, provisioned Prometheus + Jaeger datasources and the starter dashboard `observability/grafana/dashboards/pede-aqui-backend.json`). Details in `docs/local-development.md`.
- Tests: `TracingAutoConfigurationTest` (no endpoint → no exporter; endpoint without collector → starts; disabled → no exporter), `TracingE2ETest` (own context, unsampled, unreachable collector: problem `traceId` = MDC = JSON log line; outbound `traceparent`; metrics wired), `TracingDisabledApiTest`, `BusinessMetricsTest`.
- Out of scope here (AWS, LAC-50 §2/§4–6): ADOT Collector → X-Ray, CloudWatch Logs retention, alarms, managed dashboards.
